# Deckard v1.0 Specification

**Status:** Draft  
**Gem:** `deckard`  
**Executable:** `deckard`  
**Ruby namespace:** `Deckard`  
**Supported ORM:** ActiveRecord 8+  
**Supported database:** PostgreSQL  
**Purpose:** Stream relational objects between Rails environments

## 1. Summary

Deckard copies selected ActiveRecord objects and their associated records from one Rails environment into another.

Its primary use case is copying production data into a local development database for debugging, support investigations, and realistic development work:

```bash
remote_command="deckard -r /app/config/environment -d 'User.find(1234)'"

ssh example.org "$remote_command" \
  | deckard -r ./config/environment -l
```

Deckard is a direct resurrection of the original `replicate` gem’s operating model:

1. Boot the source Rails application.
2. Evaluate a Ruby expression or dump script.
3. Traverse the selected objects and associations.
4. Stream each object to standard output as it is discovered.
5. Pipe that stream to Deckard in the destination Rails application.
6. Insert each object with a new local primary key.
7. Rewrite foreign keys using a source-to-destination ID map.

Deckard does not introduce a server, direct database-to-database connection, configuration file, query language, or elaborate CLI.

## 2. Design principle

Deckard favors sensible defaults with simple, explicit configuration.

The original `replicate` README is the API baseline.

An original example should generally translate to Deckard by making only these changes:

| Original | Deckard |
|---|---|
| `gem install replicate` | `gem install deckard` |
| `require "replicate"` | `require "deckard"` |
| `replicate ...` executable | `deckard ...` executable |
| `replicate_associations` | `replicate { associations ... }` |
| `replicate_natural_key` | `replicate { natural_key ... }` |
| `replicate_omit_attributes` | `replicate { omit_fields ... }` |

Everything else should remain conceptually and syntactically close to the original.

In particular, Deckard v1.0 will not introduce:

- `deckard dump` and `deckard load` subcommands.
- A `--root` option.
- CLI association paths.
- Named extraction plans.
- Presets.
- A global Deckard configuration DSL.
- A second API for operations already supported by `dump`.
- A direct source-database connection from the destination.
- A required intermediate file.

The source objects are simply the objects passed to `dump`, whether implicitly through `-d` or explicitly in a dump script.

## 3. v1.0 goals

Deckard v1.0 must provide:

### 3.1 Streaming

Objects are written to the output stream as they are traversed and loaded by the destination as they arrive.

Neither side materializes the complete object graph, SQL dump, or encoded stream in memory.

The source may retain a compact set of identities already dumped. The destination may retain a compact source-to-destination ID map. Both are necessary for deduplication and foreign-key remapping.

### 3.2 Primary-key remapping

By default, every newly replicated ActiveRecord row receives a primary key generated by the destination PostgreSQL database.

Source primary keys are used only to identify objects within the stream. They are not inserted into destination primary-key columns.

Given:

```text
Source:

users.id = 100
orders.id = 500
orders.user_id = 100
```

Deckard may produce:

```text
Destination:

users.id = 8431
orders.id = 19002
orders.user_id = 8431
```

An unrelated local row with `id = 100` or `id = 500` remains untouched.

### 3.3 ActiveRecord 8+

The gem supports ActiveRecord 8 and follows current ActiveRecord APIs.

The initial dependency should be:

```ruby
spec.add_dependency "activerecord", ">= 8.0", "< 9.0"
```

Deckard must not preserve the original gem’s version-specific callback monkeypatches or deprecated persistence APIs.

### 3.4 PostgreSQL

Deckard v1.0 supports PostgreSQL as both source and destination.

PostgreSQL-specific insertion behavior may be used internally, particularly `INSERT ... RETURNING` through ActiveRecord.

The object stream itself must not be a sequence of PostgreSQL SQL statements. This keeps eventual MySQL support possible without changing the basic dump API.

### 3.5 Original configuration surface

The original README’s small configuration surface remains available:

- Additional associations.
- Natural keys.
- Explicit field omissions and association omissions.
- `dump_replicant` and `load_replicant` hooks.

These features should remain small and direct rather than becoming a generalized plugin or policy framework.

## 4. Explicit non-goals for v1.0

Deckard v1.0 does not include:

- Anonymization or masking.
- MySQL, SQLite, or other database adapters.
- Complete database cloning.
- Background synchronization.
- Change-data capture.
- Resumable imports.
- Checkpointing.
- A web interface.
- A daemon or server.
- Automatic SSH or deployment-platform orchestration.
- SQL dump generation.
- Fixture management.
- Association limits.
- Nested association configuration syntax.
- Custom transformation pipelines.
- A public database-adapter framework.
- Primary-key preservation.
- Automatic matching based on every unique index.
- Support for every ActiveRecord association variation.
- Support for every PostgreSQL type or schema feature.
- Optimizations that make the implementation substantially harder to understand.

Deckard should fail clearly when it encounters an unsupported case rather than adding generalized machinery to accommodate it.

## 5. Installation

Add Deckard to each application environment from which it will dump or load data:

```ruby
gem "deckard"
```

Then install it:

```bash
bundle install
```

Or install it directly:

```bash
gem install deckard
```

The source and destination should run compatible Deckard versions.

## 6. Command-line interface

Deckard intentionally retains the original `-r`, `-d`, and `-l` interface.

### 6.1 Dumping an expression

Evaluate a Ruby expression and dump the resulting object or objects to standard output:

```bash
deckard -r ./config/environment -d "User.find(1)" > user.dump
```

Diagnostic output goes to standard error:

```text
dumped 4 total objects:

Profile        1
User           1
UserEmail      2
```

The value returned by the expression may be:

- One object implementing `dump_replicant`.
- An ActiveRecord instance.
- An ActiveRecord relation.
- An enumerable of dumpable objects.

Deckard automatically calls `dump` on the expression result. The expression
is evaluated in the same context as a dump script (section 6.3), so it may
also call `dump` itself.

There is no `--root` concept or option.

### 6.2 Requiring the application environment

The `-r` option requires a Ruby file before evaluating or loading anything:

```bash
deckard -r ./config/environment -d "User.find(1)"
```

This normally boots Rails and loads the application’s model classes. After
requiring the file, Deckard eager loads the application (through Zeitwerk,
when present) so every model’s `replicate` block has run, and validates the
plans (section 7.5) before any dump or load begins.

### 6.3 Dump scripts

For more involved selection, use a normal Ruby file:

```ruby
# config/deckard/dump-stuff.rb

require "./config/environment"

%w[rtomayko/tilt rtomayko/bcat].each do |repo_name|
  repo = Repository.find_by_name_with_owner(repo_name)

  dump repo
  dump repo.commit_comments
  dump repo.issues
end
```

Run it with the same `-d` option:

```bash
deckard -d config/deckard/dump-stuff.rb > repos.dump
```

When the argument to `-d` resolves to a file, Deckard evaluates that file in a small context exposing:

```ruby
dump(object)
```

A script may call `dump` as many times as necessary. Command-line arguments
after the options are left in `ARGV` for the script:

```bash
deckard -r ./config/environment -d config/deckard/dump-repo.rb rtomayko/tilt
```

`-d -` reads the script from standard input instead of a file.

A dump script is ordinary trusted Ruby. Deckard does not invent a separate configuration or query language for this use case.

### 6.4 Loading

Load a Deckard stream from standard input:

```bash
deckard -r ./config/environment -l < repos.dump
```

Diagnostic output goes to standard error:

```text
loaded 1479 total objects:

CommitComment    95
Issue           101
IssueComment    427
Repository       20
User             89
```

Loading refuses to run when the application environment is production, as
reported by `Rails.env` or, without Rails, `RAILS_ENV` or `RACK_ENV`. The
refusal is a `LoadError` raised before any frame is read. `--force`
overrides it for the rare deliberate case.

### 6.5 Application output during a dump

Deckard writes its binary stream to standard output and its own diagnostics
to standard error. Requiring an application runs arbitrary boot code, and
that code may print to stdout: a logger configured with `STDOUT`, a `puts` in
an initializer, or a child process.

Before requiring the application in dump mode, Deckard duplicates the
original standard output for its own use and reopens file descriptor 1 onto
standard error. Everything the process or its children subsequently write to
stdout lands on stderr, and only the stream reaches the pipe or file. The
operator does nothing to opt in; `> user.dump` and `| deckard -l` work as
written regardless of what the application prints.

### 6.6 Direct SSH streaming

The primary remote workflow remains a normal Unix pipeline:

```bash
remote_command="deckard -r /app/config/environment -d 'User.find(1234)'"

ssh example.org "$remote_command" \
  | deckard -r ./config/environment -l
```

SSH is only the transport. Deckard does not manage SSH connections or know anything about the remote host.

### 6.7 CLI scope

The required v1.0 CLI is deliberately small:

```text
deckard -r FILE -d EXPRESSION_OR_FILE_OR_- [ARGS...]
deckard -r FILE -l [--force]
deckard --version
deckard --help
```

No additional data-selection CLI is required.

## 7. ActiveRecord model configuration

Deckard adds one configuration method to ActiveRecord models:

```ruby
replicate do
  # the replication plan
end
```

A dump starts from one model, and the developer configuring it thinks from
that model outward. The `replicate` block on that root model is the plan for
dumps rooted there: what the root carries, and, through `model`, how every
class those dumps reach is dumped and matched. One file describes the graph:

```ruby
class Order < ActiveRecord::Base
  belongs_to :customer
  has_many :line_items

  replicate do
    associations :line_items

    model "LineItem" do
      associations :adjustments
    end

    model "Customer" do
      natural_key :email
      omit_fields :password_digest
    end
  end
end
```

The block provides five methods in v1.0:

```ruby
associations
natural_key
omit_fields
omit_associations
model
```

`model` takes a class name and a block offering the other four. A dump
follows its root's plan and nothing else: `dump Order` uses Order's block for
every record it reaches, and `dump LineItem` uses LineItem's. A reached
class's own `replicate` block is not consulted, so there is nothing to merge
and no precedence to learn. A class the plan does not name is dumped with the
defaults below. Within one plan, the settings for a class apply wherever that
class appears, the root's own class included. Classes are named as strings,
so the root never forces them to load first, and they are matched through
their ancestors: an STI subclass follows the entry for its nearest declared
ancestor.

Natural keys travel with the records: each replicant in the stream carries
the attributes its plan matches it by (section 9.2), so the destination needs
no plan of its own and the source's plan drives the load.

There is no `Deckard.configure` block and no separate model concern that applications must include.

### 7.1 Association dumping

By default, dumping an ActiveRecord object includes:

1. Its supported `belongs_to` associations.
2. The object itself.
3. Its supported `has_one` associations.

`has_many` associations are not included automatically because doing so can quickly pull in a large portion of the database.

Additional associations are configured inside the `replicate` block:

```ruby
class User < ActiveRecord::Base
  belongs_to :profile
  has_many :email_addresses

  replicate do
    associations :email_addresses
  end
end
```

Dumping a user now includes its email addresses:

```bash
deckard -r ./config/environment -d "User.find(1)" > user.dump
```

`associations` is additive and may receive multiple names:

```ruby
replicate do
  associations :email_addresses, :memberships
end
```

It may also be called more than once:

```ruby
replicate do
  associations :email_addresses
  associations :memberships
end
```

Deckard does not add nested association declarations. Deeper traversal is expressed in the root's plan, model by model, or through further `dump` calls in a dump script.

For example:

```ruby
class Repository < ActiveRecord::Base
  replicate do
    associations :issues

    model "Issue" do
      associations :comments
    end
  end
end
```

Or:

```ruby
repo = Repository.find(123)

dump repo
dump repo.issues
dump repo.issues.flat_map(&:comments)
```

### 7.2 Natural keys

By default, the loader creates a new destination record and assigns it a new destination primary key.

A plan can define a natural key when existing destination records should be reused:

```ruby
class User < ActiveRecord::Base
  belongs_to :profile
  has_many :email_addresses

  replicate do
    natural_key :login
    associations :email_addresses

    model "EmailAddress" do
      natural_key :user_id, :email
    end
  end
end
```

A natural key may contain one or more attributes.

The key travels with each record in the stream. When loading a record with a natural key, Deckard:

1. Resolves any replicated foreign-key references in the natural key.
2. Looks for an existing destination record matching all natural-key attributes.
3. Updates that record if exactly one match exists.
4. Creates a new record with a new destination primary key if no match exists.
5. Fails if the lookup is ambiguous.

The source-to-destination ID map points at either the newly created record or the reused destination record.

For example:

```text
Source User id=100, login="rob"
Destination User id=8, login="rob"
```

With `natural_key :login`, Deckard maps:

```text
["User", 100] => 8
```

Dependent records are then rewritten to reference destination user `8`.

Natural keys are explicit. Deckard does not inspect all unique indexes and guess which ones should identify shared records.

### 7.3 Omitting fields

Fields may be excluded from a model's dumped attributes:

```ruby
class User < ActiveRecord::Base
  has_one :profile

  replicate do
    omit_fields :created_at, :encrypted_password
  end
end
```

Only explicitly named fields are removed. `omit_fields` does not change association
traversal. In particular, omitting a foreign-key field does not implicitly omit its
association:

```ruby
replicate do
  omit_fields :organization_id
end
```

Deckard still traverses `organization`, but `organization_id` is not included in the
dumped row. If an explicitly omitted field causes a destination constraint violation,
the load fails normally.

### 7.4 Omitting associations

Associations may be excluded from graph traversal independently of dumped fields:

```ruby
replicate do
  omit_associations :organization
end
```

Deckard does not traverse or dump the organization through this association. The source
row's attributes remain unchanged: `organization_id` is still dumped as its raw source
value because the organization was not traversed and no destination ID is available for
remapping.

This rule also applies to polymorphic associations. Given:

```ruby
class Setting < ActiveRecord::Base
  belongs_to :scope, polymorphic: true

  replicate do
    omit_associations :scope
  end
end
```

Deckard copies both `scope_id` and `scope_type` exactly as stored but does not traverse
`scope`. The application has explicitly taken responsibility for that relationship. If
the raw foreign key violates a destination constraint, the load fails normally; Deckard
does not silently remove or rewrite fields.

### 7.5 Plan validation

The plan is validated as a whole before a stream starts. The `deckard`
executable eager loads the application after requiring it, so every
`replicate` block has run, then checks the entire plan: each class named by
`model` must be a loaded ActiveRecord model, each configured association must
exist and be of a supported kind, and each natural-key or omitted attribute
must exist. Validation reports every problem at once as a
`ConfigurationError` before any record is dumped or loaded. Dumping through
the Ruby API validates each model's plan when its first record is dumped.

## 8. Traversal behavior

The default ActiveRecord traversal order is:

```text
belongs_to associations
current record
has_one associations
explicitly configured associations
```

This ordering ensures that a record normally appears after the records referenced by its foreign keys.

For example:

```ruby
class Order < ActiveRecord::Base
  belongs_to :customer
  has_many :line_items

  replicate do
    associations :line_items
  end
end

class LineItem < ActiveRecord::Base
  belongs_to :order
  belongs_to :product
end
```

A stream may be ordered as:

```text
Customer
Order
Product
LineItem
Product
LineItem
```

### 8.1 Deduplication

A dumped object is identified by:

```ruby
[type_name, source_id]
```

The source retains a compact set of identities already dumped.

If several orders reference the same customer, that customer is written once. Every order reference points to the same source identity, which the destination resolves to one destination ID.

### 8.2 Relations and collections

ActiveRecord relations and collection associations should be iterated in batches where practical.

Deckard must not convert an entire relation into an array merely to begin dumping it.

Arrays and other enumerables supplied by application code are iterated normally.

### 8.3 Repeated dumps

Calling `dump` on an object that has already been emitted does not emit it again.

The root's plan on the first traversal determines which of that object’s associations are followed during that traversal.

When a dump script needs an additional collection, the simple and explicit solution is to dump that collection:

```ruby
dump repo
dump repo.events
```

Deckard does not maintain a second graph of visited association edges solely to merge every possible later traversal request.

### 8.4 Constraints and unsupported graphs

Deckard relies on reference ordering rather than disabling PostgreSQL constraints.

Ordinary inverse-association cycles are stopped by the dumped-object identity set.

A record reached again while its own dump is in progress (through a parent’s
configured collection, for example) is emitted at that point once its own parents are
in the stream, as in the original `replicate`; the outer traversal’s later write is a
no-op.

A graph requiring a record to reference another new record that cannot be emitted first is unsupported in v1.0 and produces an error.

Deckard does not add placeholder rows, deferred repair passes, or automatic constraint disabling to accommodate such graphs.

## 9. Stream format

Deckard uses a small, versioned Ruby `Marshal` stream.

This closely follows the original gem and avoids introducing SQL generation, JSON type conversion, or an additional serialization dependency.

### 9.1 Stream frames

A stream contains:

1. One version header.
2. Zero or more replicant tuples.
3. One successful-end marker.

Conceptually:

```ruby
Marshal.dump([:deckard, 1], output)

Marshal.dump(
  ["User", 1234, { "name" => "Rob" }, ["login"]],
  output
)

Marshal.dump([:deckard_end, 1], output)
```

The exact internal constants may differ, but the protocol must be explicitly versioned.

A dump produced by the old `replicate` gem is not required to load in Deckard.

### 9.2 Replicant tuple

Every dumped object is represented by:

```ruby
[type, source_id, attributes, natural_key]
```

Where:

- `type` is a class-name string.
- `source_id` identifies the object in the source environment.
- `attributes` is a hash with string keys and serializable Ruby values.
- `natural_key` is the array of attribute names the destination matches an
  existing record by, empty when the record is always inserted.

The combination of `type` and `source_id` must be unique within the stream.

### 9.3 References

An attribute that references another replicated object is represented using the original-style reference tuple:

```ruby
[:id, "User", 1234]
```

For example:

```ruby
[
  "Order",
  500,
  {
    "number" => "R-123",
    "user_id" => [:id, "User", 1234]
  },
  ["number"]
]
```

The referenced object must appear earlier in the stream.

Only foreign keys that hold the referenced record's primary key are encoded
this way. A `belongs_to` whose `primary_key` option names another column
(`belongs_to :account, primary_key: :login`) stores a natural value; the
referenced record is still dumped first, but the field is copied as-is.

When the destination loads the order, it replaces the reference tuple with the destination ID mapped from:

```ruby
["User", 1234]
```

### 9.4 Completion marker

The end marker distinguishes a complete stream from a source process that failed after writing some complete records.

The loader commits only after reading a valid end marker.

Unexpected end-of-file causes the destination transaction to roll back.

### 9.5 Stream trust

Ruby `Marshal` is unsafe for untrusted input.

Deckard streams must only be loaded from trusted applications and operators. The normal documented transport is authenticated SSH.

Deckard is an internal operator tool, not a public import format or network service.

## 10. Loading ActiveRecord records

ActiveRecord classes provide the default class method:

```ruby
load_replicant(type, source_id, attributes)
```

It returns:

```ruby
[destination_id, object]
```

The default implementation:

1. Receives attributes after all reference tuples have been resolved.
2. Looks up an existing record when the model has a natural key.
3. Otherwise prepares a new record.
4. Writes attributes without validations or callbacks.
5. Allows PostgreSQL to assign a new primary key for new records.
6. Returns the destination ID and loaded object.

### 10.1 New records

New records should be inserted through a current ActiveRecord API that:

- Bypasses validations.
- Bypasses callbacks.
- Applies ActiveRecord type serialization.
- Omits the source primary key.
- Uses PostgreSQL `RETURNING` to obtain the new primary key.

A straightforward v1 implementation may use one-row `insert_all!` calls:

```ruby
result = insert_all!(
  [attributes.except(primary_key)],
  returning: [primary_key]
)

destination_id = result.rows.first.first
object = find(destination_id)
```

Record-by-record insertion is acceptable for v1.0.

Streaming correctness, understandable code, and the extension API take priority over maximizing bulk-insert throughput.

### 10.2 Existing natural-key records

An existing record matched by natural key is updated using an API such as:

```ruby
record.update_columns(attributes.except(primary_key))
```

This intentionally bypasses callbacks and validations.

Attributes omitted from the stream are not changed.

### 10.3 Existing local data

Without an explicit natural key, Deckard never updates or deletes an existing destination record.

A conflict on another unique constraint causes the load to fail and roll back.

Deckard does not automatically convert every unique-constraint failure into an upsert.

### 10.4 Transactions

The ActiveRecord load runs inside one destination database transaction.

The transaction commits only after the valid end marker.

Malformed input, unresolved references, missing classes, schema errors, constraint violations, or insertion failures roll back the load.

Custom `load_replicant` implementations may perform external side effects that PostgreSQL cannot roll back. That is the application author’s responsibility.

### 10.5 Database constraints

Deckard leaves PostgreSQL constraints enabled.

It does not:

- Set `session_replication_role`.
- Disable referential integrity.
- Drop constraints.
- Delay all constraints automatically.

Correct reference ordering and ID remapping are the normal mechanism for satisfying constraints.

## 11. Validations, callbacks, and explicit post-load work

Deckard’s default ActiveRecord loader bypasses all validations and callbacks.

It is a data-copying tool, not an application workflow runner.

Applications that explicitly need post-load behavior may override `load_replicant`, retaining the original extension shape:

```ruby
class User < ActiveRecord::Base
  def self.load_replicant(type, id, attributes, natural_key)
    destination_id, object = super

    object.register_in_redis
    object.some_other_callback

    [destination_id, object]
  end
end
```

Deckard must not build a callback framework around this.

The class method override is the escape hatch.

## 12. Custom objects

Deckard retains the original duck-typed custom-object interface.

This keeps the core dumper and loader small: ActiveRecord support is itself an implementation of the same replicant protocol.

### 12.1 `dump_replicant`

A custom object may implement:

```ruby
dump_replicant(dumper)
```

The method writes one replicant through:

```ruby
dumper.write(type, id, attributes, natural_key = [])
```

Example:

```ruby
class User
  attr_reader :id
  attr_accessor :name, :email

  def dump_replicant(dumper)
    attributes = {
      "name" => name,
      "email" => email
    }

    dumper.write(self.class, id, attributes)
  end
end
```

### 12.2 `load_replicant`

The corresponding class implements:

```ruby
load_replicant(type, source_id, attributes, natural_key)
```

`natural_key` is the array of attribute names the record travels with
(section 9.2); a custom loader may use or ignore it. Example:

```ruby
class User
  def self.load_replicant(type, id, attributes, natural_key)
    user = User.new
    user.name = attributes["name"]
    user.email = attributes["email"]
    user.save!

    [user.id, user]
  end
end
```

Deckard stores the returned destination ID in its ID map.

The v1.0 guarantee of callback-free PostgreSQL insertion applies to Deckard’s ActiveRecord implementation, not to arbitrary custom-object loaders.

There is no custom-object registry or adapter API. Deckard constantizes the streamed type and calls the class method.

## 13. Supported ActiveRecord shape

Deckard v1.0 targets ordinary Rails models with:

- One conventional primary-key column.
- Integer, bigint, or database-generated UUID primary keys.
- Conventional `belongs_to`.
- Conventional polymorphic `belongs_to`.
- Conventional `has_one`.
- Explicitly selected conventional `has_many`.
- Explicitly selected reverse polymorphic `has_one` and `has_many`.
- Normal `class_name` and `foreign_key` association options.
- Attributes serializable by Ruby `Marshal` and writable through ActiveRecord.

The following are explicitly not required for v1.0:

- Composite primary keys.
- HABTM join-table replication.
- `has_many :through`.
- `has_one :through`.
- Associations targeting non-primary unique keys.
- Complicated STI dispatch.
- Cross-database associations.
- Models without a usable primary key.
- Deferrable dependency cycles.
- Custom PostgreSQL types that do not survive the normal ActiveRecord attribute interface.
- External files or ActiveStorage blobs.
- Counter-cache repair.
- Materialized-view refreshes.
- Search-index updates.
- Redis or other external-store synchronization, except through an explicit application override.

These cases may work accidentally in simple forms, but they are not part of the v1.0 contract.

## 14. Errors

Deckard should use a small error hierarchy:

```ruby
Deckard::Error
Deckard::ConfigurationError
Deckard::DumpError
Deckard::OutputError
Deckard::LoadError
Deckard::UnsupportedAssociation
Deckard::UnresolvedReference
Deckard::InvalidStream
Deckard::InsertError
```

Errors should include enough context to identify the problem:

```text
Deckard::UnsupportedAssociation:
Author.bookmarked_posts is a has_and_belongs_to_many association, which deckard does not support
```

```text
Deckard::UnresolvedReference:
Order(500).user_id references User(1234), which has not been loaded
```

```text
Deckard::ConfigurationError:
Order has no :line_item association
"Customr" is named in a replicate block, but is not a loaded ActiveRecord model
```

```text
Deckard::InsertError:
User source_id=42 could not be inserted:
duplicate key value violates unique constraint users_email_key
```

Normal errors must not print complete attribute hashes or sensitive production values.

All failures return a nonzero process status.

`OutputError` reports failures writing the dump stream. A closed output pipe
retains its concise broken-pipe diagnostic.

## 15. Diagnostics

The data stream uses standard output.

Human-readable status uses standard error.

While standard error is a terminal, both dump and load keep a single
progress line updated with the running object count. A pipe or log file
receives only the completion report.

Dump completion should show counts by type:

```text
dumped 1479 total objects:

CommitComment    95
Issue           101
IssueComment    427
Repository       20
User             89
```

Load completion should show equivalent counts:

```text
loaded 1479 total objects:

CommitComment    95
Issue           101
IssueComment    427
Repository       20
User             89
```

Application output that would otherwise reach stdout is redirected to stderr
(section 6.5). The default output should remain useful in an SSH pipeline
without becoming a logging subsystem.

## 16. Proposed internal structure

Deckard should remain a small library.

A sufficient initial structure is:

```text
Deckard::CLI
Deckard::Dumper
Deckard::Loader
Deckard::ModelConfig
Deckard::ActiveRecord
Deckard::Status
```

Responsibilities:

### `Deckard::CLI`

- Parse `-r`, `-d`, and `-l`.
- Reserve standard output for the stream before requiring the application.
- Require the application environment, then eager load it.
- Validate every plan before streaming.
- Evaluate dump expressions and scripts.
- Connect standard input and output to the dumper or loader.
- Return useful process statuses.

### `Deckard::Dumper`

- Accept objects through `dump`.
- Deduplicate by type and source ID.
- Call `dump_replicant`.
- Write versioned Marshal frames.
- Track counts.
- Write the successful-end marker.

### `Deckard::Loader`

- Validate the stream header.
- Read records incrementally.
- Resolve reference tuples.
- Call `load_replicant`.
- Maintain the source-to-destination ID map.
- Validate the end marker.
- Manage the destination transaction.
- Track counts.

### `Deckard::ModelConfig`

- Hold one root's plan: its own associations, optional natural key, and
  field and association omissions, plus a `model` entry of the same shape
  for each class its dumps reach, whether or not those classes have loaded.
- Back the `replicate do ... end` DSL.
- Resolve the plan for a root, and the entry for a reached class, through
  their ancestors.
- Validate every plan on demand, reporting every problem.

### `Deckard::ActiveRecord`

- Install the `replicate` model method.
- Implement ActiveRecord `dump_replicant`.
- Implement ActiveRecord `load_replicant`.
- Add nothing else to model classes: those three are the only methods
  Deckard defines on `ActiveRecord::Base`. Traversal and loading are plain
  objects inside the module, not private model methods.
- Traverse supported reflections.
- Encode foreign-key references.
- Insert or update rows without callbacks.

### `Deckard::Status`

- Count objects by type.
- Write concise progress and completion information to standard error.

Deckard should not add abstract base classes, service registries, dependency-injection containers, protocol plugins, or database-adapter frameworks for hypothetical future requirements.

## 17. Correctness invariants

Deckard v1.0 must maintain these invariants:

1. A source object is emitted no more than once.
2. An emitted object is identified by its type and source ID.
3. A referenced object appears before the object that references it.
4. A source primary key is not inserted as the primary key of a newly created destination record.
5. Every loaded object produces a source-to-destination ID mapping.
6. Every reference tuple resolves through that mapping.
7. Multiple references to one source object resolve to one destination object.
8. ActiveRecord validations and callbacks do not run in the default loader.
9. Existing local records are changed only when a natural key explicitly matches them.
10. Standard output from dump mode contains only the stream.
11. A stream without a successful-end marker does not commit.
12. The loader never silently leaves an unresolved source foreign key in a destination row.
13. Unsupported behavior raises rather than being approximated.

## 18. Acceptance criteria

Deckard v1.0 is ready when the following work against ActiveRecord 8 and PostgreSQL.

### 18.1 Original-style expression dump

```bash
deckard -r ./config/environment -d "User.find(1)" > user.dump
```

produces a loadable stream.

### 18.2 Original-style dump script

A file containing repeated calls to:

```ruby
dump object
```

can dump multiple records, relations, and collections.

### 18.3 Direct SSH pipeline

```bash
ssh example.org \
  "deckard -r /app/config/environment -d 'User.find(1234)'" \
| deckard -r ./config/environment -l
```

loads records without an intermediate file.

### 18.4 Default association behavior

`belongs_to` and `has_one` records are included automatically.

`has_many` records are not included automatically.

### 18.5 Model association configuration

```ruby
replicate do
  associations :email_addresses
end
```

causes the configured collection to be included.

### 18.6 Root-model plan

```ruby
class Order < ActiveRecord::Base
  replicate do
    associations :line_items
    model "LineItem" do
      associations :adjustments
    end
  end
end
```

dumps each line item's adjustments whether `LineItem` loads before or after
`Order`; `dump LineItem.first` follows LineItem's own block, not Order's; and
a plan naming a missing class, association, or attribute fails with
`ConfigurationError` before any record is dumped or loaded through the
executable.

### 18.7 ID remapping

Source primary keys are replaced with destination-generated keys, and every supported foreign key points at the correct destination row.

### 18.8 Shared dependencies

Two records referencing the same source record produce only one destination copy of the shared record.

### 18.9 Natural keys

```ruby
replicate do
  natural_key :login
end
```

reuses and updates an existing destination record and maps dependent records to its destination ID.

### 18.10 Field and association omission

```ruby
replicate do
  omit_fields :created_at
  omit_associations :profile
end
```

omits the explicitly named field and does not traverse the explicitly named association.
Each decision is independent: association omission never removes fields, and field
omission never changes graph traversal.

### 18.11 Callback bypass

Models with failing validations or observable creation callbacks still load, and the callbacks do not run.

### 18.12 Explicit load hook

A model override of:

```ruby
self.load_replicant
```

can call `super`, perform explicit post-load work, and return the destination ID and object.

### 18.13 Custom objects

Objects implementing `dump_replicant` and classes implementing `load_replicant` can participate in the same stream as ActiveRecord records.

### 18.14 Streaming

The destination begins processing records before the source has completed traversal.

Memory does not grow with the combined size of all record attributes or the encoded stream.

Memory may grow with the source identity set and destination ID map.

### 18.15 Atomic database loading

A malformed stream, truncated stream, unresolved reference, or PostgreSQL insertion error rolls back all destination database changes made by the load.

### 18.16 Clear unsupported-case errors

HABTM associations, through associations, composite primary keys, and unsupported dependency cycles produce specific errors rather than corrupted data.

### 18.17 Boot-log-safe output

A dump whose application prints to stdout while booting still produces a
valid stream on standard output; the application's output appears on
standard error.

## 21. Final v1.0 decisions

Deckard v1.0 will:

- Preserve the original `replicate` command shape.
- Use `deckard` as the gem and executable name.
- Use `Deckard` as the Ruby namespace.
- Use `replicate do ... end` on a root model as the plan for everything its dumps reach, and nothing else.
- Expose only `associations`, `natural_key`, `omit_fields`, `omit_associations`, and `model` inside that block.
- Retain dump expressions and ordinary Ruby dump scripts.
- Retain `dump_replicant` and `load_replicant`.
- Stream directly over standard input and output.
- Use a versioned Marshal stream.
- Remap IDs by default.
- Support ActiveRecord 8+.
- Support PostgreSQL only.
- Keep `belongs_to` and `has_one` automatic.
- Keep collection associations opt-in.
- Bypass callbacks and validations.
- Avoid introducing a new query language, configuration framework, or verbose CLI.

The governing product test is simple:

> A developer who remembers the original `replicate` gem should be able to use Deckard immediately, with the whole plan for a dump gathered into one `replicate` block on its root model.
